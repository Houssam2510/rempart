Le moteur

Un scan, étape par étape

Ce qui se passe quand tu tapes rempart scan . — en 0,5 à 3 secondes sur un vrai projet.

1

Trouver les fichiers

Il demande la liste à Git. Ce qui est dans .gitignore n'est jamais envoyé sur GitHub, donc il ne le signale pas : ton .env local n'est pas une fuite, un .env committé en est une.

2

Lancer les 13 scanners

Chacun reçoit les mêmes fichiers et renvoie des « findings ». Si un scanner plante, les autres continuent : l'erreur apparaît dans le rapport.

3

Enlever le bruit

Règles désactivées dans .rempart.toml, commentaires rempart:ignore, doublons.

4

Appliquer ce qu'il a appris

Les faux positifs que tu as marqués disparaissent ; la confiance de chaque règle est recalculée.

5

Chercher les chemins d'attaque

Il combine des résultats de domaines différents en scénarios complets.

6

Noter et trier

Chaque finding reçoit un risque de 0 à 100 ; le dépôt reçoit une note de A à F.

Anatomie d'un finding

La note du dépôt

Pourquoi 50 alertes identiques ne coulent pas la note : les répétitions d'une même règle comptent 1, ½, ⅓… Beaucoup de problèmes différents, eux, font chuter la note.

Exemple concret 1 · flux de données

L'injection SQL cachée dans une variable

Un outil naïf ne regarde que la ligne execute(q) : elle a l'air propre. Rempart remonte d'où vient q.

def report(cur):
    # ① vient de l'utilisateur → user_id est « tainted »
    user_id = request.args["id"]
    # ② chaîne construite avec user_id → q est « dynamic »
    q = f"SELECT * FROM t WHERE id = {user_id}"
    # ③ puits SQL + variable marquée → ALERTE
    cur.execute(q)

Le correctif proposé

q = "SELECT * FROM t WHERE id = %s"
cur.execute(q, (user_id,))
# la base reçoit la valeur à part : impossible d'injecter du SQL

Python

Analyse de l'arbre syntaxique (AST), variable par variable. Chaque fonction du dépôt est résumée, donc la donnée traverse les fonctions et les fichiers (voir page 15).

JavaScript / TS

Suit req.body, request.json(), searchParams et la déstructuration const { file } = req.query.

Limite honnête

En JS/TS, le suivi traverse les fonctions d'un même fichier, pas encore les imports entre modules. Là, c'est l'agent IA qui prend le relais.

Exemple concret 3 · priorisation

Toutes les CVE ne se valent pas

Le score CVSS dit « à quel point ce serait grave ». Il ne dit pas « est-ce que quelqu'un l'exploite ». Rempart ajoute deux preuves : la liste KEV de la CISA (exploitée pour de vrai) et EPSS (probabilité d'exploitation dans les 30 jours).

La formule, en clair

risque = gravité × confiance
si EPSS connu → on le mélange
si dans KEV → au moins 95

À retenir

KEV est un plancher, pas un bonus : un fait (« c'est exploité ») passe devant une prédiction. C'est la logique de la directive BOD 22-01 de la CISA, la même que dans ton projet triage.

Bonus atteignabilité. Pour chaque paquet vulnérable, Rempart regarde si ton code l'importe vraiment : « imported by your code », « declared », ou « transitive, not imported directly ». Un paquet jamais importé garde son alerte, mais avec une confiance réduite.

Exemple concret 4 · images

Ouvrir une image Docker… sans Docker

Une image, c'est une pile de couches (des archives .tar). Rempart les télécharge depuis le registre, les superpose, et ne garde que les fichiers utiles.

Fin de vie (EOL)

Alpine 3.18 → fin mai 2025. Une version morte ne reçoit plus de correctifs : les nouvelles CVE resteront ouvertes pour toujours.

Secrets oubliés

Un .env copié dans l'image, une variable API_TOKEN dans la config ou l'historique de build : quiconque fait docker pull peut les lire.

Le tri intelligent

Une CVE de plus de 3 ans que Debian n'a jamais corrigée est souvent contestée ou mineure : gardée, mais classée LOW (sauf si KEV).

En pratique

$ rempart image alpine:3.18
alpine:3.18 · Alpine Linux v3.18 · 10 packages · user root · built 2025-02-14
  HIGH  Base OS release is end-of-life      Alpine Linux v3.18 reached end-of-life on 2025-05-09.
  MEDI  Image runs as root by default       No non-root USER is configured.
  MEDI  Image has not been rebuilt in over a year   Built 602 days ago (2025-02-14).

Sortie réelle, image tirée de Docker Hub en 1 seconde. Aucune CVE listée : normal, une version morte ne reçoit plus d'avis de sécurité, c'est justement pour ça que la fin de vie est signalée.

Exemple concret 5 · vérification en direct

Une clé fuitée : incident ou ménage ?

Une clé déjà révoquée, c'est du nettoyage d'historique. Une clé qui marche encore, c'est un incident. Avec --verify-secrets, Rempart pose la question au fournisseur.

24 fournisseurs

AWS (STS)GitHubGitLabSlackStripe liveStripe testOpenAIAnthropicHugging FacenpmSendGridDigitalOceanResendLinearNotionSentryAirtableFigmaGroqReplicatePostmanTelegramMapboxNew Relic

Le cas AWS

Il faut l'ID de clé et le secret à côté, puis signer la requête avec l'algorithme SigV4. Rempart le fait avec la seule bibliothèque standard Python, et un test vérifie que la signature est identique, octet pour octet, à celle de botocore.

Règle d'éthique

Uniquement sur tes propres dépôts. Rien n'est écrit avec la clé, rien n'est stocké : seule l'identité renvoyée (ex. « GitHub user octo ») apparaît.

En pratique

$ rempart scan . --verify-secrets
  CRIT  Hard-coded GitHub token  ci.sh:1
        GitHub token found (ghp_************A5). VERIFIED LIVE: GitHub user octo. Rotate it now.
        id 3c1e… · SEC-GITHUB-TOKEN · risk 90 · live-secret

Exemple tiré des tests automatiques (jeton factice, réponse de GitHub simulée).

Exemple concret 6 · cloud en direct

Ton compte AWS, tel qu'il est vraiment

Terraform dit ce que l'infrastructure devrait être. rempart cloud aws regarde ce qu'elle est, en lecture seule, dans toutes les régions en parallèle.

Identités

MFA du root, clés du root, mots de passe, MFA des utilisateurs, clés de plus de 90 jours, politiques *:*

Stockage

S3 public (ACL, politique, compte), HTTPS non imposé (87 % des comptes AWS en 2026)

Réseau & calcul

Ports SSH/BD ouverts (IPv4 et IPv6), IMDSv1, snapshots et AMI publics, flow logs

Données

RDS public, non chiffré, sans sauvegarde ; chiffrement EBS par défaut ; rotation KMS

Détection

CloudTrail multi-régions, GuardDuty, AWS Config, Access Analyzer

Serverless

URL Lambda sans auth, runtimes Lambda obsolètes

Kubernetes

Endpoint EKS ouvert à internet

L'agent IA

Un relecteur qui lit le code pour toi

Une règle voit un motif. Elle ne sait pas si eval reçoit une valeur d'une table constante. L'agent (un modèle d'IA d'Anthropic, famille Opus) va lire, chercher, puis trancher.

Exemple de verdict réel (test)

faux positif « eval ne reçoit que des valeurs de la table constante OPS ; l'utilisateur choisit seulement la clé. » app.py:4,8

confirmé « request.args['d'] est concaténé dans une commande shell. » app.py:12

4 garde-fous

① lecture seule, sur les fichiers du scan uniquement
② le contenu du dépôt est « non fiable » (anti prompt-injection)
③ boucle bornée + repli automatique si le modèle refuse
④ il ne supprime jamais un résultat

Coût affiché à la fin (tokens et dollars estimés). Il envoie des extraits de ton code à l'API Anthropic : à ne pas utiliser sur du code que tu n'as pas le droit de partager.

Il apprend

Chaque verdict rend l'outil plus précis

Chaque règle a une « confiance de départ ». Tes verdicts la font monter ou descendre. C'est une formule bayésienne simple, mesurée sur un vrai essai.

rempart triage f26cf13b27 --fp --note "contrôle d'accès dans le middleware"
rempart triage c54d4f3be8 --tp
rempart learn          # ce que l'outil a appris, règle par règle
rempart history        # évolution de la note, nouveaux / corrigés, temps moyen de correction

Toi = décision

Un faux positif que tu marques disparaît des scans suivants de ce projet.

L'IA = indice

Un verdict de l'agent compte 0,5 et ne peut jamais fermer un résultat ni écraser le tien.

Règle bruyante

5 faux positifs et moins de 25 % de précision : la sévérité baisse d'un cran automatiquement.

Le vocabulaire

Glossaire visuel

Les mots que tu entendras en entrevue, en une ligne chacun.

SAST

Analyse statique : lire le code sans l'exécuter.

SCA

Analyse des dépendances : quelles bibliothèques, quelles versions, quelles failles connues.

CVE / CWE

CVE = une faille précise (CVE-2025-55182). CWE = la famille de faille (CWE-89 = injection SQL).

CVSS · EPSS · KEV

Gravité théorique · probabilité d'exploitation · preuve d'exploitation réelle.

Taint (souillure)

Marquer une donnée venant de l'utilisateur et la suivre jusqu'à un endroit dangereux.

SSRF

Faire envoyer au serveur une requête vers une adresse choisie par l'attaquant.

IMDS (v1 / v2)

Service interne d'EC2 qui donne les clés du rôle. v2 exige un jeton : bloque les SSRF simples.

RLS

Row Level Security : la base filtre les lignes selon l'utilisateur (Supabase).

IaC

Infrastructure décrite en code (Terraform) : on peut la scanner avant de la créer.

SARIF

Format standard de résultats de sécurité, affiché par GitHub dans l'onglet Security.

MCP

Protocole qui permet à un assistant IA d'appeler des outils comme Rempart.

EOL

End of life : version qui ne reçoit plus de correctifs de sécurité.

Whiteout

Fichier spécial .wh.nom qui supprime un fichier d'une couche d'image précédente.

Faux positif

Alerte sur du code sûr. L'ennemi n°1 d'un scanner.

Nouveau en 0.3 · flux de données

Suivre la donnée d'une fonction à l'autre

Avant, le suivi s'arrêtait au bord d'une fonction. Maintenant, Rempart résume chaque fonction du dépôt : ce qui entre, ce qui ressort, et ce qui atteint un endroit dangereux.

Ce que ça a changé, mesuré

Et en JS/TS ? Les fonctions d'un même fichier sont résumées aussi : gitLog(req.query.branch) est signalé si gitLog passe son paramètre à exec. Un exec interpolé sans donnée de requête tracée devient MEDIUM (« à relire »), comme en Python.
15
Nouveau en 0.3 · graphe de ressources

Un chemin d'attaque prouvé, pas supposé

Deux failles dans le même dépôt peuvent concerner deux machines qui ne se parlent pas. Rempart construit maintenant le graphe de ce que ton dépôt déploie, et ne dit « lié » que s'il trouve une route entre les deux.

Ce qui crée un lien

Une référence Terraform, un depends_on ou un réseau compose, un sélecteur Kubernetes, un compte de service, et l'image que ton dépôt construit, retrouvée dans le déploiement qui la lance.

Lié → CRITICAL

La route s'affiche en vert dans le terminal. C'est elle qu'on montre en revue : on voit la chaîne, maillon par maillon.

Pas de lien → un cran plus bas

« Co-occurrence » : les pièces existent, mais rien ne prouve qu'elles se touchent. Message explicite, sévérité réduite, confiance 0,5.

Sur tes 10 projets : aucun chemin d'attaque n'est sorti, lié ou non. C'est cohérent avec l'étiquetage à la main : aucun ne contenait une vraie chaîne. Un outil qui invente des chemins perd la confiance en une semaine.

Nouveau en 0.3 · au quotidien

Rempart en continu

Un scan ponctuel vieillit le jour même. Quatre outils pour que la sécurité suive le rythme du code.

--baseline origin/main

Juger une PR sur ce qu'elle ajoute

Rempart scanne la branche cible dans une copie temporaire (git worktree) et masque tout ce qui existait déjà. Une PR n'hérite plus du passif du dépôt. L'action GitHub le fait par défaut et peut commenter la PR.

--git-history

Les secrets qui n'ont jamais vraiment disparu

Effacer une clé d'un fichier ne l'efface pas des commits. Rempart relit chaque ligne ajoutée de chaque branche. Sur un de tes projets, il a retrouvé trois clés (OpenAI, Azure Storage, Google) restées dans l'historique d'un docker-compose.yml.

upgrade plan

Une ligne par paquet, pas 40 alertes

« next 14.2.32 → 15.5.24 : corrige 25 avis sur 25, utilisé par ton code, version majeure ». La plus petite version qui règle tout, en restant sur la même version majeure quand c'est possible. Les dépendances de dev descendent d'un cran.

rempart watch

Ne voir que la différence

Rempart surveille le dépôt et rescanne à chaque modification. Il n'affiche que ce qui apparaît (+) ou disparaît (−). Pour la nuit, un workflow planifié relance tout avec les CVE du jour.

Et l'agent IA prouve ce qu'il confirme

# rempart-proofs/test_proof_export.py · écrit par l'agent, jamais exécuté par Rempart
def test_export_escapes_its_folder(client, monkeypatch):
    sent = {}
    fake = lambda p: sent.setdefault("path", p) or ""
    monkeypatch.setattr("files.export.send_file", fake)
    client.get("/export?file=../../etc/passwd")
    # passe aujourd'hui, échoue une fois la faille corrigée
    assert sent["path"].endswith("etc/passwd")
Mesurer l'agent : rempart agent-eval le fait passer sur 9 petits dépôts étiquetés : 7 vraies failles, 5 pièges (liste blanche dans un helper, nettoyage dans un autre fichier, appelants toujours constants). Il donne le taux d'accord, les vraies failles conservées et les faux positifs écartés.
